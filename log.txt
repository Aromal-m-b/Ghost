# Findings and design so far

Nothing is validated end to end yet. I've built and tested the identity resolver and the log parser. The evidence normalizer is written, but its first run failed on a path bug (the manifest paths already start with `evidence/`), so I haven't confirmed it works.

## 1. What the data looks like

**The task is entity resolution plus state reconstruction.** Evidence is global and shared across cases. Each file is a multi-user snapshot, and no file says which case it belongs to.

**Linking a record to a person** works through these identifiers:
- current and historical emails
- `sha256(lowercase email)`. I verified the hash matches `user_identities.csv`.
- phones, from the audit log
- `user_id` references (`customer_reference`, `subject_reference`)
- `lookup_key` / `correlation_key` fields in log traces

All 518 requests resolve to a user. 418 match a current email and 100 match a historical one.

**Evidence formats:**
- 4 PDFs and 11 PNGs (the PNGs need OCR or vision)
- 7 JSON shapes
- 3 SQL families: inventory dumps with a scope table, primary/replica drift dumps, and failover dumps
- 6 log dialects: kv, JSON, bracket, pipe, syslog and cloud-runtime. All 1,000+ lines parse.
- a text handover file

**Resource state at `audit_at`** comes from the latest observation captured at or before `audit_at`. Absence appears in several forms: HTTP 404, `NOT_FOUND`, a null profile, `result=miss`, `rows=0`, or omission from a snapshot that covers the whole system.

**Replica drift:** a record that survives in any copy counts as remaining. For example, `account_994` exists in the read replica but not in the primary.

**Support records have two subtypes:**
- messages are redacted, because they hold shared context
- attachments are deleted

A stable `customer_reference` is allowed on redacted support records and tombstones. For analytics it still counts as attributable, so it must be anonymized.

**Answer-format regularities from the 32 samples:**
- Step order is findings, then remediation, then verification.
- Remediation order is disable flows, block restores, delete, redact, anonymize. Within each group, rows sort by system and then resource ID.
- Verification always includes the account (`VERIFY_RECORD_ABSENT`) and the security audit record (`VERIFY_RECORD_PRESENT`) when one exists.
- `COMPLETE` cases cite evidence on every step. `INCOMPLETE` remediation and verification steps use an empty `evidence_id`.
- The samples contain no `NOT_APPLICABLE` case. The activity log has 10 `CLASSIFY_REQUEST` events that classify requests as non-deletion, so those exist in the real set.

## 2. Problems I found

1. **Orphan resources.** Some already-scrubbed resources (a 404 account, a fully nulled analytics row) carry no identifier in the evidence. Example: `account_3136` should belong to `s.yoon04@gmail.com`, but only the activity stream mentions it, and the stream names no user. Activity timing is the only link: events fall shortly before `reported_at`, and the reported status correlates with the result (`NOT_STARTED` ↔ `FAILED`, `COMPLETE` ↔ `SUCCESS`, `PARTIALLY_COMPLETE` ↔ `PARTIAL`). That still leaves ties between cases that share the same `reported_at`. I'll handle it with elimination and global assignment, and I expect some residual error there.
2. **Resource meaning varies by evidence format.** `analytics_9914` is a marketing opt-in record sitting in the analytics system, so it should be deleted, not anonymized. I handle this through a `subtype` field.
3. **Evidence after `audit_at`** must be ignored, including for citations.
4. **Possible trap:** a security audit record whose `retention_until` is already past at `audit_at` shouldn't be retained. I haven't seen a case of it yet.
5. **The 12 `LINK_RESOURCE_IDENTITY` events** line up with the 11 images and 4 PDFs. They are the grounded link for media evidence, since OCR is noisy ("areedi433@" for "areed1433@").

## 3. Architecture

A fixed graph where the code owns control flow and the LLM only chooses among tools and handles genuine ambiguity.

```
INTAKE → INTENT → [NOT_APPLICABLE → EMIT]
                → IDENTITY → INVESTIGATE (loop) → RECONSTRUCT → POLICY
                → PLAN → VALIDATE ⟲ repair → EMIT
```

**Deterministic layers (no LLM):**
- the dataset loader and identity resolver (done)
- the evidence normalizer, which turns every format into one observation record (written, unvalidated)
- policy evaluation from `deletion_rules.csv`
- step ordering and JSON serialization
- a validator that checks schema, step numbering, phase order, no evidence after `audit_at`, and `[]` for `NOT_APPLICABLE`

**Where the LLM is used:**
- **INTENT:** a keyword prefilter handles the clear cases. The LLM is called only for ambiguous or multilingual text (the samples include Spanish, French and Japanese).
- **INVESTIGATE:** the loop chooses the next tool from a registry, using a constrained JSON schema with an enum of tool names. Tools include scanning for linking keys, reading SQL replicas, OCR or vision on a specific image, resolving orphans, and `finish`. The LLM sees compact summaries (which files hit which identifiers), not raw files.
- **Vision:** it reads screenshots when OCR is unreliable.
- **Repair:** if validation fails, it gets one targeted repair attempt.

**Efficiency:** responses are cached by input hash, calls are batched per snapshot, and a token tracker feeds `usage_report.md`.

**Fallback:** every LLM decision has a deterministic equivalent, so the pipeline runs without an API key. A router test with a fake LLM client exercises the call path.

## 4. Limitations

- **No API key here.** I can't run live LLM calls in this sandbox. I'll build and test the LLM path against a stub and unit-test the schema handling. The usage report will show only what actually ran, which means zero calls if I run offline.
- **Orphan linking won't be perfect.** I'll measure it on the 32 samples and report the error rate.
- **Accuracy is measured only on the 32 samples.** The hidden 518 are mostly the bulk families, so I'll add custom test cases and be explicit about that gap.
